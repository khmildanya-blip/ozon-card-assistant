# ТЗ для фронтенда — первое демо

**Статус:** черновик для согласования  
**Этап:** первое демо проекта

## 1. Цель демо

Показать, как пользователь по фотографии начинает создание карточки товара для Ozon:

1. загружает фото товара;
2. сервис определяет товар и подбирает категорию и тип товара Ozon;
3. backend запрашивает у Ozon атрибуты для этой категории и типа;
4. фронтенд показывает форму с полями, которые продавцу нужно заполнить вручную.

В первом демо нужно показать распознавание/определение по фото, работу RAG в процессе определения или поиска релевантной информации и получение реальных атрибутов категории через Ozon API. Значения полей на этом этапе пользователь вводит сам.

## 2. Сценарий пользователя

1. Пользователь открывает стартовый экран.
2. Загружает фотографию товара — через выбор файла или перетаскивание.
3. Проверяет превью и при необходимости заменяет фото.
4. Нажимает **«Определить товар»**.
5. Видит состояние обработки.
6. Получает результат определения: название/тип товара и предложенную категорию Ozon.
7. Подтверждает категорию или выбирает другую, если сервис ошибся.
8. Сервис получает список атрибутов для выбранных категории и типа товара.
9. Пользователь видит сгруппированную форму атрибутов и заполняет её вручную.

В первом демо достаточно показать получение и заполнение полей. Отправка готовой карточки на создание товара в Ozon в объём не входит, если отдельно не будет согласована.

## 3. Экраны и элементы интерфейса

### 3.1 Стартовый экран

- Название сервиса и короткое объяснение: загрузите фото товара, чтобы определить категорию и получить форму атрибутов Ozon.
- Большая заметная зона загрузки.
- Выбор файла и drag-and-drop.
- Подсказка о допустимом формате и лимите размера файла — согласовать с backend.
- Основная кнопка **«Определить товар»**; недоступна, пока фото не выбрано.

### 3.2 Фото выбрано

- Превью выбранного изображения.
- Возможность удалить или заменить фото.
- Понятное сообщение, если файл не является изображением или превышает лимит.

### 3.3 Определение товара и категории

- Состояние загрузки и обработки.
- Короткий статус, например: **«Распознаём товар и подбираем категорию Ozon…»**.
- После ответа показать предполагаемое название/тип товара и категорию.
- Дать пользователю подтвердить категорию или выбрать другую из предложенных/найденных вариантов до запроса атрибутов.
- Если уверенность определения доступна от backend, можно показать её; не придумывать значение на фронте.

### 3.4 Форма атрибутов

- Заголовок с выбранной категорией и типом товара.
- Поля строятся по ответу Ozon API, а не захардкожены во фронтенде.
- Атрибуты сгруппированы по группам, если группы приходят в ответе.
- Обязательные поля визуально отмечены.
- Для каждого поля показываются название и описание/подсказка, если они есть в ответе.
- Тип поля определяется по схеме атрибута: текст, число, одиночный выбор, множественный выбор и другие поддерживаемые типы.
- Если для атрибута есть справочник значений, пользователь выбирает значение из списка; список подгружается через backend по мере необходимости.
- Поддержать множественные значения и лимит значений, если они указаны в метаданных атрибута.
- Необязательные поля также отображаются, но не мешают понять, какие поля обязательны.
- Кнопка **«Сохранить черновик»** может быть локальной/демонстрационной; сохранение в аккаунт и историю относится ко второму демо.

### 3.5 Ошибки и пустые состояния

Предусмотреть отдельные понятные состояния:

- товар или категория не определены;
- для категории не удалось получить атрибуты;
- справочник значений временно недоступен;
- ошибка сети/API;
- Ozon вернул пустой список атрибутов.

Пользователь должен иметь возможность повторить запрос, вернуться к выбору категории или загрузить другое фото.

## 4. Визуальное направление

В перспективе продукт может развиться в сервис с карточками товаров и механикой, похожей на дейтинг-приложение. В первом демо можно использовать чистое карточное оформление фотографии, определения и формы, но без свайп-механики.

Для первого демо:

- современный, дружелюбный и простой интерфейс;
- один основной сценарий без лишних разделов;
- сначала одна форма одного товара, не лента товаров;
- адаптивная версия для мобильного и десктопного экранов;
- блоки товара и атрибутов проектировать переиспользуемыми, чтобы позже собрать из них карточки/ленту.

## 5. Граница первого и второго демо

### Первое демо

- загрузка фотографии;
- распознавание товара и определение категории/типа;
- получение атрибутов выбранной категории через Ozon API;
- отображение формы;
- ручное заполнение полей пользователем;
- RAG в согласованной части определения/поиска информации.

### Вторая итерация

- регистрация и пользовательский профиль;
- база данных и сохранение прошлых карточек;
- нейросеть предлагает или заполняет значения атрибутов по фотографии;
- пользователь проверяет и редактирует предложения нейросети;
- более полноценный интерфейс карточек; к этой итерации можно вернуться к механике ленты и свайпов.

### До защиты

- парсинг источников;
- расширенное распознавание и связанный с ним полный сценарий создания карточки.

### Не показываем в первом демо

- свайпы, лайки, дизлайки, мэтчи и бесконечную ленту;
- автоматическое заполнение атрибутов нейросетью;
- регистрацию, сохранение истории и полноценную базу карточек;
- создание/публикацию товара на Ozon;
- административную панель.

## 6. Требования к интеграции

- Фронтенд вызывает API нашего backend; `Client-Id` и `Api-Key` Ozon хранятся только на backend и не попадают в браузер.
- Для получения структуры категорий и типов backend использует актуальный метод дерева категорий и типов Ozon.
- Для выбранных `description_category_id` и `type_id` backend получает список атрибутов категории. В текущей документации Ozon это методы `/v1/description-category/tree` и `/v1/description-category/attribute`; для справочников значений предусмотрен `/v1/description-category/attribute/values`.
- Значения атрибутов, их обязательность, тип, группы и справочники берутся из ответа Ozon; фронтенд не должен подменять их статическими полями.
- Согласовать с backend-командой внутренние endpoints, форматы запроса/ответа, ошибки, пагинацию справочников и ограничения файла. Контракт нашего backend в этом ТЗ пока не фиксируется.
- Для разработки интерфейса допустимы моковые данные, явно отделённые от реального API.

## 7. Критерии готовности

- Пользователь загружает фото и видит превью.
- После отправки видит состояние распознавания.
- Результат определения включает категорию и тип товара либо позволяет выбрать их вручную.
- После подтверждения категории отображаются атрибуты, полученные через backend из Ozon API.
- Обязательные поля, описания, типы и варианты выбора отображаются корректно по ответу API.
- Пользователь может вручную заполнить поля формы.
- Сетевые ошибки, ошибка определения и пустые результаты имеют понятные состояния.
- Можно изменить фото или категорию и повторить запрос без перезагрузки страницы.
- В первом демо нет свайпов и автоматического заполнения значений нейросетью.
- Основной сценарий работает на мобильной и десктопной ширине.

## 8. Вопросы для согласования

1. На старте сервис работает только с товарами для Ozon или планируется сразу несколько маркетплейсов?
2. Название нужно строго русское и описательное или можно короткое бренд-слово вроде «Кардо»?
3. В первом демо пользователь должен выбирать категорию только если распознавание ошиблось, или категория всегда показывается на подтверждение перед загрузкой атрибутов?
4. Какие именно функции RAG должны быть видны пользователю в первом сценарии: поиск подходящей категории, объяснение результата или ответы/подсказки по атрибутам?
